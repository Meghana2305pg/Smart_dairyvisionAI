## EXECUTIVE SUMMARY

The current DairyVision AI architecture implements:

1. **✅ Cow Registration** - FULLY IMPLEMENTED
   - Page: `webapp/screens/herd.py` (registration form)
   - Service: `CowService.register_cow()`
   - Repository: `CowRepository` → Supabase `cows` table
   - Status: Production-ready

2. **✅ Master vs Daily Data Separation** - PARTIALLY IMPLEMENTED
   - **MASTER DATA (Static Cow Attributes):** Stored in `cows` table
   - **DAILY DATA (Observations):** Stored in `observations` table
   - Status: Schema exists but relationship is weak (relies on cow_id matching)

3. **✅ Daily Data Entry** - FULLY IMPLEMENTED
   - Page: `webapp/screens/operations.py` (Daily Operations workflow)
   - Service: `ObservationService.record_observation()`
   - Repository: `ObservationRepository` → Supabase `observations` table
   - Status: Production-ready with 5-step guided workflow

4. **✅ Digital Twin** - IMPLEMENTED AS IN-MEMORY STATE MACHINE
   - **NOT** a persistent data structure in Supabase
   - **IS** an in-memory Python object (`CowTwin` class)
   - Creates immutable snapshots in `InMemorySnapshotStore` (not persisted to Supabase)
   - Status: Currently not persistent; snapshots are memory-only

5. **✅ Predictions** - FULLY INTEGRATED
   - Model: XGBoost milk yield prediction
   - Trigger: Called during observation recording or manual prediction
   - Stored: In `CowTwin.latest_prediction` (memory); referenced but not persisted to Supabase

6. **⚠️ Persistence Gap** - CRITICAL FINDING
   - **Twin snapshots generated but NOT persisted to Supabase**
   - Snapshots exist only in `InMemorySnapshotStore` during session
   - **Data is LOST on page refresh or session end**
   - Referenced Supabase table `twin_snapshots` exists in code but is never written to

## 5. DIGITAL TWIN - CURRENT IMPLEMENTATION

### 5.1 What IS the Digital Twin?

The Digital Twin is **NOT a data structure in Supabase**. It is:

**✅ What it IS:**
- Python in-memory object: `CowTwin` dataclass
- Located in: `webapp/digital_twin/cow_twin.py`
- Lifecycle: Created per session, scoped to browser session
- State machine: Evolves based on observations and AI results
- Purpose: Encapsulates current cow state + AI outputs for UI display

**❌ What it is NOT:**
- Not persisted to database
- Not shared across browser sessions
- Not a traditional data model
- Not accessible across users/devices

### 5.2 Architecture

**File:** `webapp/digital_twin/cow_twin.py`

```python
@dataclass
class CowTwin:
    cow_id: str
    name: str | None = None
    state: TwinState = field(default_factory=TwinState)
    observation_history: list[Observation] = field(default_factory=list)
    latest_observation: Observation | None = None
    intelligence: TwinIntelligence = field(default_factory=TwinIntelligence)
    memory_store: InMemorySnapshotStore = field(default_factory=InMemorySnapshotStore)
    latest_prediction: dict[str, Any] | None = None
    latest_health: dict[str, Any] | None = None
    latest_explanation: list[dict[str, Any]] | None = None
    recommendations: list[dict[str, Any]] = field(default_factory=list)
```

### 5.4 Data Consumed

**Input Sources:**
1. ✅ Registered cow data from `cows` table
2. ✅ Daily observations from `observations` table (processed on demand)
3. ✅ ML predictions (generated in-memory)
4. ✅ Health assessments (generated in-memory)

**NOT Consumed:**
- ❌ Previous snapshots (never loaded from database)
- ❌ Historical AI outputs (re-computed each observation)

### 5.5 State Changes

When daily observation recorded:

```
1. Observation created
   ↓
2. CowTwin.record_observation(observation)
   - observation_history.append()
   - latest_observation = observation
   - state.observations.append()
   - state.refresh_timestamp()
   ↓
3. CowTwin.refresh_from_ai(base_temp, base_hum)
   - TwinIntelligence.analyze_observation()
     ├─ predict_milk_yield()
     ├─ get_health_alerts_for_input()
     └─ get_explanation_for_input()
   - state.predictions.append()
   - state.health_assessments.append()
   - state.explanations.append()
   - recommendations = build_recommendations()
   - state.recommendations = []
   - state.status = _classify_status()
   ↓
4. _store_snapshot() creates TwinSnapshot
   - memory_store.save_snapshot(snapshot)  ← In-memory
   - state.context["snapshot_count"] += 1
   ↓
5. RESULT: Twin state updated, snapshot in memory
   - On page refresh: ALL LOST
```

### 5.7 Critical Finding: Non-Persistence

**⚠️ SNAPSHOTS ARE NOT PERSISTED**

Referenced in code:
```python
# dashboard_repository.py
def get_snapshots(self) -> list[dict[str, Any]]:
    return self.client.list("twin_snapshots")

# dashboard_service.py:67
snapshots = self.repository.get_snapshots()
```

**BUT:** `twin_snapshots` table is **never written to**. The only write happens to in-memory store:
```python

self.memory_store.save_snapshot(snapshot)  # ← InMemorySnapshotStore only!
```

**Consequence:**
- Snapshots created but lost on session end
- Dashboard shows empty snapshots (queries empty table)
- Twin state not recoverable after page refresh
